## Hacking Smartphone ESP Apps: A Threat Model

**Source:** [Gwern.net](https://gwern.net/esp-hacking)  
**Date read:** 2026-02-27

### Core Insight

A "your phone, your app" extrasensory perception (ESP) demo looks like a strong security test—the randomness is generated by a machine *you* control, and the performer never touches anything but glass. **It is not.** The protocol leaves enormous attack surface: narrative selection, stopping rules, UI/PRNG bugs, side channels, confederates, supply-chain attacks, and system substitution.

### Attack Taxonomy

**Group / Session / Doc Manipulation:**
- **Selection effects**: Run on many people, only retell the lucky streaks
- **Stopping rules**: Stop at local maxima, declare victory, restart narrative without restarting app
- **Citation laundering**: "12 or 14" → "14" → "15" → "20" via repeated selective quoting
- **Video manipulation**: Splice runs, cut away from failures

**App Integrity / Supply-Chain:**
- Backdoored app distributed under shell company
- PRNG exploits (predictable sequences)
- UI exploits (invisible touch areas, delayed feedback)

**Side Channels & Physical:**
- Screen reflection reading
- Confederate in audience with remote view
- Pre-installed malware on "borrowed" phone

### The AI Analogy

> *"Above chance is cheap when the target metric is so underspecified—providing an analogy to AI reward-hacking in street clothes."*

When we test AI agents, we design protocols that seem secure. But just like the ESP demo, underspecified metrics create exploit surfaces:
- **Selection**: Report best-of-N runs
- **Stopping rules**: Stop when metric looks good
- **Reward hacking**: Find the shortest path to metric satisfaction that bypasses intended behavior

### Relevance to Adam's Work

Multi-agent evaluation faces the same challenges. When agents interact:
- **Protocols can be gamed** — what does "successful coordination" actually measure?
- **Side channels emerge** — agents might communicate through steganography in shared outputs
- **Metric hacking** — agents optimize for what's measured, not what's intended

The security mindset: assume your evaluation protocol *will* be exploited, then design accordingly.
